1. Introduction

1.1    Purpose
This Software Design Document (SDD) describes the architecture and system design of Elha2,
release 1.0: the subsystems and components it is built from, how they collaborate, the data they
store, the algorithms of the main operations, and the user interface. It translates the requirements
in the Elha2 Software Requirements Specification (SRS) [1] into a representation that programmers
can implement.

   Its intended audience is the five-member development team, who use it as the primary reference
for writing code; our instructor and teaching assistants, who assess the design at each milestone;
and future maintainers. The SDD is updated at the end of every sprint together with the SRS, and
every change is recorded in the revision history.


1.2    Scope
Elha2 is an Arabic-first, AI-assisted mobile app and web portal that reduces food waste in Egypt
at three points: Prevent (a smart household pantry that fills itself from receipts, photos and voice
notes and warns before food spoils), Sell (businesses list surplus at a discount for pickup) and
Donate (unsold food goes to NGOs automatically, and households can donate sealed items). Every
verified action is measured in kilograms, Egyptian pounds, CO2 e and meals.

   The goals are to cut household food waste, to make household tracking effortless, to recover
business surplus as affordable food, to redistribute food to people in need, and to measure impact
credibly, while keeping food, users and data safe (SRS Section 1.4, Product Scope). The benefits
are lower grocery bills, recovered revenue for businesses, a steady flow of safe food for NGOs, and
credible data for SDG 12.3 reporting.

   This SDD covers the whole system specified in the SRS, so that the architecture does not need
to change as later features are added. The preliminary design (architecture and data architecture,
Chapters 3 and 4) covers all 14 features. The detailed design (component algorithms and screens,
Chapters 5 and 6) is given for the 39 stories we implement during the course (SRS Section 6.6) and
is extended sprint by sprint.


1.3    Overview
Chapter 2 gives a general description of the system’s functionality, context and design. Chapter 3
presents the architecture: the subsystems and their responsibilities (Section 3.1), their object-
oriented decomposition with component, sequence and interface descriptions (Section 3.2), and the
rationale for the design (Section 3.3). Chapter 4 describes how data is stored and organised, with
Software Design Document for Elha2                                                                          Page 2


UML class diagrams and a data dictionary. Chapter 5 gives pseudocode for the main operations
of each component. Chapter 6 describes the user interface with low-fidelity wireframes. Chap-
ter 7 traces every component and every SRS requirement to each other. The appendices hold the
deployment design and the declaration of AI use.

2. System Overview

2.1      Functionality
Elha2 serves six kinds of user through two clients. Households use the mobile app to keep a smart
pantry (filled from receipts, barcodes, photos and voice notes and checked once a week), receive
expiry reminders, cook suggested Egyptian recipes, buy discounted surplus, donate sealed food to
NGOs and see their impact. Businesses, NGOs, administrators and government analysts use the
web portal to list surplus and confirm pickups, receive donation offers, run the platform, and
export anonymised data. The functions are grouped into 14 features (E1 to E13), specified as 100
user stories in SRS Chapter 4.


2.2      Context
Elha2 is a new, self-contained product. Figure 2.1 shows its context: the people and organisations
it serves and the external systems it depends on for login, push notifications, maps, payments, AI
models, product data, weather and grocery emails. Every external system is reached through an
adapter or the AI gateway, so it can be replaced without changing the rest of the code.

2.3      Design Summary
Elha2 is a client–server system with three tiers. Two clients, a Flutter mobile app and a React
web portal, talk to one NestJS backend over HTTPS and WebSockets. The backend is a modular
monolith: one deployable service divided into eight domain modules and five platform services that
interact only through declared interfaces. A separate Python service runs the machine-learning
models. PostgreSQL with PostGIS stores all data, locations and the job queue. Text and barcode
recognition run on the phone, and every call to a hosted AI model goes through one AI gateway
that validates results and falls back to a non-AI path on failure. Chapter 3 explains this design
and the patterns it uses.

3. System Architecture

3.1      Architectural Design

3.1.1     Subsystems and Responsibilities

two clients, one for people on phones (households and deal seekers) and one for organisations on
desktops (businesses, NGOs, administrators, analysts). All business rules live in one backend, so
both clients behave the same and every rule is enforced in one place. Numeric machine learning,
which needs Python libraries and long-running training jobs, is separated into its own service.
External services sit behind interfaces that Elha2 owns. Figure 3.1 shows the major subsystems,

3.1.2    How the Subsystems Collaborate
 Clients to backend. The mobile app and the web portal call the backend’s REST API for
  every read and write, and keep a WebSocket open for live listing quantities and order status.
  Each request carries a Firebase ID token, which the backend verifies before routing.

 Inside the backend. Requests enter through the API layer and are handled by one domain
  module (Section 3.2.1). Domain modules call platform services (AI gateway, impact ledger, noti-
  fications, scheduler, adapters) and, where needed, each other, always through named interfaces.

 Backend to ML service. The backend calls the ML service over internal HTTP for shelf-
  life estimates and recommendations. The ML service reads its training data from a read-only
  database view and never writes business data.
Software Design Document for Elha2                                                                            Page 8


 Backend to external services. Payments, maps, product data and inbound email go through
  the integration adapters; language, vision and speech models go through the AI gateway; push
  notifications go through Firebase Cloud Messaging.

 Time-based work. The scheduler starts jobs (daily digests, end of pickup window, offer time-
  outs, no-shows, nightly training) that call the owning module, so timed work follows the same
  rules as user requests.

3.1.5       Technical Feasibility
Every part of the design uses mature, documented technology that the team can learn within the
semester. All AI capabilities use existing models or services (SRS Section 2.2.1); we train only
small tabular models. The stack runs on free tiers and student credits. The three riskiest technical
questions (right-to-left layouts in Flutter, OCR accuracy on real Egyptian receipts, PostGIS dis-
tance queries) are answered by technical spikes in Sprint 1. Each of the five team members owns
one area of the design (mobile app, web portal, backend domain modules, AI gateway and ML
service, data and DevOps), and the declared interfaces let the five areas be built in parallel.


3.2         Decomposition Description
We use an object-oriented description. Section 3.2.1 decomposes the backend into modules,
Section 3.2.2 the AI and ML subsystem and Section 3.2.3 the clients. Section 3.2.4 specifies the
interfaces between them, and Section 3.2.5 shows how they collaborate in sequence diagrams. The
object model (UML class diagrams, including the Organisation generalisation hierarchy and the
aggregation of pantry items in a household) is in Chapter 4.

3.2.1       Backend API Subsystem
The backend has three layers (Figure 3.2). The API layer receives every request, checks the Firebase
token and validates input. The eight domain modules hold the business rules, one per area of the
backlog. The five platform services are shared by all domain modules. Modules call each other
only through the named interfaces, which keeps the code testable and lets team members work on
different modules in parallel.

3.2.5       Sequence Diagrams
Scan a receipt (UC-05).         Figure 3.4 shows how the components of Figures 3.1 to 3.3 work
together when a household user scans a receipt. OCR and masking run on the phone, so only
masked text reaches the backend. The AI gateway calls the LLM, validates the reply and records
its cost before the Pantry module adds expiry estimates. Nothing is saved until the user confirms.

Reserve and collect a bag (UC-22, UC-25). Figure 3.5 shows the marketplace handover.
The stock update is atomic, so two buyers can never get the last bag. At pickup, the Orders module
checks the code against the branch and asks the Impact ledger to record the saving exactly once.

Route unsold food to an NGO (UC-33).                This flow is started by the scheduler rather than
by a user. Its algorithm is given in Section 5.9.

1. When a listing is created, the Scheduler queues a job for the end of its pickup window.

2. At that time, the job calls IStock.unsoldAtWindowEnd; if anything is left and auto-donation is
   on, it calls Donations.

3. Donations finds verified NGOs within range whose food types, capacity and hours match, ordered
   with the business’s default partner first.

4. It sends an offer to the first NGO and queues a 30-minute expiry job; if the offer is declined or
   expires, it moves to the next NGO.

5. When an NGO accepts, the business is notified; the handover is confirmed by code and recorded
   in the Impact ledger.

4.1.3    Key Data Design Decisions
 Locations. Listings, branches, NGOs and drop-off points store a PostGIS geography(Point)
  column with a GiST index, so radius searches stay under 2 s (NFR-03). Public responses about
  users return only a distance and an area name, never an exact point.

 Impact ledger. ImpactRecord rows are append-only and unique per source action (an order,
  a donation or a pantry item). Each row stores the factor version it used, so totals never change
  when factors are updated, and nothing is counted twice (US-9.03). ImpactFactor rows are
  versioned and never overwritten (US-9.02).

 Stock.   A reservation reduces Listing.quantity in one conditional update (quantity >=
  requested) inside a transaction, which guarantees that a bag is never sold twice (NFR-06).

 Offline copy. The mobile app keeps the household’s pantry in SQLite. Changes are queued
  with timestamps and merged per field on reconnect, and every change can be undone (NFR-21,
  R-13; algorithm in Section 5.11).

 Personal data. Card data is never stored (NFR-11). AI photos live in Cloud Storage under
  a 24-hour deletion rule (NFR-14). AIRequestLog stores no personal data. Account deletion
  removes personal fields within 30 days and keeps only anonymised impact rows (US-1.08).

 Jobs. pg-boss keeps scheduled jobs in PostgreSQL, so a job and the data it changes can be
  committed in the same transaction, and failed jobs are retried (NFR-19).

 Backups. Daily encrypted backups, with a 24-hour recovery point and a 4-hour recovery time
  (NFR-20).

5. Component Design
This chapter takes a closer look at what each component does. For the operations behind the
stories we implement during the course, it gives the algorithm in pseudocode (PDL) with the local
data it uses. Operations that only read or write one record (for example editing a profile) are not
repeated here. The pseudocode is refined into code during each sprint; when the implementation
differs, this chapter is updated with change markings.

      Conventions: CamelCase names are operations of the component; tx is a database transaction;
config is a platform setting changeable by administrators (US-13.04); comments start with ▷.


5.1      AI Gateway: Run an AI Task
Used by every AI feature (US-14.01, NFR-22, NFR-30). Local data: the versioned prompt template
and JSON schema for the task, and a cache keyed by a hash of the input.

Algorithm 1 RunTask(task, input, user)
Input: task name, input (already masked on the phone), calling user
Output: result, confidence, fallbackUsed
 1: template ← PromptTemplate(task, config.promptVersion[task])
 2: key ← Hash(task, template.version, input)
 3: if cache contains key then return cache[key]

 4: if MonthlyCost(user) ≥ config.aiBudgetPerUser then return (Fallback(task, input), 0,
      true)
 5: for attempt ← 1 to 2 do                                                               ▷ one retry
 6:      reply ← Provider(config.provider[task]).call(template.fill(input), timeout = 15 s)
 7:      if reply arrived and reply matches template.schema and SafetyFilter(task, reply) passes
      then
 8:           Log(task, model, latency, cost, reply.confidence, fallback = false)
 9:           cache[key] ← reply; return (reply.result, reply.confidence, false)
10: Log(task, model, latency, cost, 0, fallback = true)
11: return (Fallback(task, input), 0, true)                     ▷ e.g. raw OCR lines for manual entry

US-2.01, 2.02, 14.03. The first part runs on the phone; the rest in the Pantry module. Local data:
the receipt draft (masked lines and draft items).

Algorithm 2 ScanReceipt(photo) and ConfirmDraft(draftId, edits)
 1: lines ← MLKitOCR(photo)                                                         ▷ on the phone
 2: lines ← MaskPersonalData(lines)                             ▷ names, phone numbers, card digits

5.3     Expiry: Estimate an Expiry Date
US-3.01. Local data: the catalogue’s base shelf life per storage place; a seasonal factor table. The
ML service refines the rule-based estimate when it has enough data.

Algorithm 3 Estimate(catalogueItem, storage, purchasedOn)
Output: expiry date and its source
 1: if a printed date was captured then return (printedDate, printed)

 2: days ← catalogueItem.baseShelfLife(storage)
 3: if storage ̸= freezer and month of purchasedOn ∈ {May, . . . , September} then
 4:     days ← ⌊ days × config.summerFactor ⌋                         ▷ shorter in Egyptian summer
 5: (mlDays, ok) ← MLService.ShelfLife(catalogueItem, storage, purchasedOn)              ▷ optional
 6: if ok then days ← Min(days, mlDays)                                           ▷ be conservative
 7: return (purchasedOn + days, estimated)




5.4     Pantry: Choose the Weekly Check Cards
US-2.09. Local data: for each item, the expected usage date from its category’s typical consumption

Algorithm 4 WeeklyCheckCards(household)

6. Human Interface Design

6.1     Overview of User Interface
Mobile app (households and deal seekers). The app opens on Home, which shows the items
closest to expiry, today’s deals nearby and the user’s impact this week. A bottom bar gives five
tabs:

 Home: at-risk items with one-tap recipe and donate actions; recipe suggestions (Use it up).

 Pantry: items grouped by fridge, freezer and cupboard and coloured by urgency. A large Add
  food button opens the capture methods: scan receipt, scan barcode, photo, voice and manual.
  After any AI capture the user sees a review screen and confirms with one tap. Once a week the
  pantry offers the 30-second swipe check.

 Deals: a map and a list of nearby surplus; a listing page with price, pickup window, allergens
  and Reserve; after reserving, a QR code and 4-digit code for pickup.

 Donate: choose sealed pantry items to donate, see partner drop-off points on a map, or buy a
  bag for an NGO.

 Impact: kilograms, pounds, CO2 e and meals saved; the monthly waste rate against the Egyptian
  average; How we calculate.

Web portal (businesses, NGOs, administrators, analysts).                After sign-in the portal shows
only the areas of the user’s role in a left-hand menu. Businesses see Today’s orders (with Scan
pickup code), Listings, Donations, Impact and Settings. NGOs see Offers, Pickups and Impact. Ad-
ministrators see Verification, Moderation, Disputes, Settings and Analytics. Analysts see Exports.

Feedback to the user.        Every action gets visible feedback: a snackbar for success (“7 items
added”), inline errors next to the field, a spinner with text for AI work longer than 1 s (“Reading
your receipt. . . ”), confidence percentages and orange highlighting on uncertain AI results, an offline
banner, and an Undo for 10 s after automatic pantry changes. Push notifications open the related
screen directly.

Language and accessibility.        Arabic with a right-to-left (mirrored) layout is the default and
English is available; the wireframes below are shown in English for readability. Every control has
a text label and a screen-reader label, touch targets are at least 48 dp, and colour is never the only
signal (SRS NFR-16 to NFR-18).

Appendix A: Deployment Design
The backend and the ML service are stateless containers, so they can scale horizontally behind a
load balancer (NFR-05). The hosting provider will be confirmed in Sprint 1 (SRS TBD-06); the
table names the planned option for each part.

Node                Runs                                                 Planned hosting

User phones         Mobile app                                           Google Play internal testing;
                                                                         Apple TestFlight
Browsers            Web portal (static build)                            Firebase Hosting
API containers      Backend API with the Scheduler workers               Managed containers (e.g.
                                                                         Google Cloud Run)
ML containers       ML service; nightly training job                     Same platform as the API
Database            PostgreSQL 16 with PostGIS                           Managed PostgreSQL (e.g.
                                                                         Cloud SQL or Supabase),
                                                                         daily backups
Firebase            Authentication, FCM, Cloud Storage                   Google Firebase



    There are three environments: local (Docker Compose on each laptop), staging and demo.
GitHub Actions runs linting, unit tests and the AI accuracy report (US-14.02) on every merge,
and deploys to staging when the tests pass. Secrets such as API keys live in the platform’s secret
manager, never in the repository.


Appendix B: Design Change Procedure
The course requires both documents to be updated every sprint with tracking of changes [2]. At
each sprint review we:

1. list the stories completed and any requirement that changed in the SRS, and use the requirements
   matrix (Chapter 7) to find the affected components;

2. update the affected diagrams, data dictionary entries, pseudocode and wireframes (replacing
   wireframes with screenshots of the delivered screens);

3. mark new or changed text with \chg{version}{...} (or \chgt inside tables) and removed
   text with \del{version}{...}, so the changes appear in blue and red with the version in the
   margin;

4. add a row to the revision history and tag the commit in GitHub (for example docs-v1.1), so
   every version of the SDD can be retrieved.
