1. Introduction

1.1     Purpose
This Software Design Document (SDD) explains how we will build Elha2, release 1.0. It shows the
main parts of the system, what each part does, how the parts work together, what data we store,
and what the screens look like. It turns the requirements in the Elha2 Software Requirements
Specification (SRS) [1] into a design.

    We update it at the end of every sprint together with the SRS and record each change in the
revision history.


1.2     Scope
Elha2 is an Arabic-first mobile app and web portal, helped by AI, that reduces food waste in Egypt
in three ways: Prevent (a smart pantry that fills itself from receipts, photos and voice notes and
warns before food spoils), Sell (businesses sell surplus food at a discount for pickup) and Donate
(unsold food goes to NGOs, and households can donate sealed items). Every confirmed saving is
measured in kilograms, Egyptian pounds, CO2 e and meals.

    Our goals are to cut household food waste, make tracking food effortless, turn business surplus
into affordable food, get food to people in need, and measure the impact honestly, while keeping
food, users and data safe (SRS Section 1.4). Users save money, businesses recover revenue, NGOs
get a steady supply of safe food, and partners get reliable data for SDG 12.3 reporting.

    The architecture and data design (Chapters 3 and 4) cover all 14 features in the SRS, so the
design does not have to change when later features are added. The screens (Chapter 5) cover the
39 stories we build during the course (SRS Section 6.6) and grow sprint by sprint.


1.3     Overview
Chapter 2 describes what the system does and who it serves. Chapter 3 presents the architecture:
the main parts and their jobs, the specific architectural style and patterns we use, how the archi-
tecture supports each quality requirement (with a deployment view), the AI models and how their
input is built, how the parts talk to each other, and why we chose this design. Chapter 4 shows
how data is stored, with UML class diagrams and a data dictionary. Chapter 5 shows the user
interface as simple wireframes. Chapter 6 links every part of the design to the SRS requirements
it satisfies. The appendix declares how we used AI in writing this document.

2. System Overview

2.1      Functionality
Elha2 serves six kinds of user through two apps. Households use the mobile app to keep a smart
pantry (filled from receipts, barcodes, photos and voice notes, and checked once a week), get expiry
reminders, cook suggested Egyptian recipes, buy discounted surplus food, donate sealed food to
NGOs and see how much they have saved. Businesses, NGOs, administrators and government
analysts use the web portal to list surplus and confirm pickups, receive donation offers, run the
platform and export anonymised data. These functions are grouped into 14 features (E1 to E14)
and written as 100 user stories in SRS Chapter 4.


2.2      Context
Elha2 is a new, standalone product. Figure 2.1 shows the people and organisations it serves and the
outside systems it uses for login, notifications, maps, payments, AI models, product data, weather
and grocery emails. Our code reaches each outside system through an adapter or the AI gateway,
so any of them can be replaced without changing the rest of the code.

2.3       Design Summary
Elha2 is a client–server system with three tiers. Two clients, a Flutter mobile app and a React web
portal, talk to one NestJS backend over the internet. More specifically, the backend is a modular
monolith: a single program split into eight feature modules and five shared services, which talk
to each other only through named interfaces. Machine learning runs in one separate microservice
written in Python. One PostgreSQL database, hosted on Supabase, stores all the data, including
locations and scheduled jobs. Supabase also provides phone login, file storage and live updates;
Firebase is used only for push notifications and to host the web portal. Text and barcode reading
happen on the phone. Every request to a hosted AI model goes through one AI gateway, which
checks the answer and switches to a non-AI option if the model fails. Chapter 3 explains this
design.

3. System Architecture

3.1     Architectural Design

3.1.1    Subsystems and Responsibilities
We split the system by who uses it and what kind of work it does, following the features and stories
in the product backlog (SRS Chapter 4):

 People on phones (households and deal seekers) use the mobile app; organisations on computers
  (businesses, NGOs, administrators, analysts) use the web portal.

 All business rules live in one backend, so both apps behave the same way and each rule is written
  only once.

 Machine learning needs Python libraries and long training runs, so it has its own ML service.

 Outside services (payments, maps, AI models) are always reached through our own interfaces,
  so we can swap them.

3.1.2    How the Subsystems Work Together
 Apps to backend. The mobile app and web portal call the backend’s REST API to read and
  save data. Users log in with Supabase Auth, and each request carries their Supabase login token,
  which the backend checks first. For live updates such as bags left and order status, the apps
  listen on Supabase Realtime channels, and the backend posts to those channels. The apps never
  read or write the database directly.

 Inside the backend. Each request enters through the API layer and is handled by one feature
  module (Section 3.2.1). Feature modules use the shared services (AI gateway, impact ledger, no-
  tifications, scheduler, adapters) and, when needed, each other, always through named interfaces.

 Backend to ML service. The backend asks the ML service for shelf-life estimates and recom-
  mendations over an internal web call. The ML service can only read its training data; it never
  changes business data.

 Backend to outside services. Payments, maps, product data, grocery emails and file stor-
  age (Supabase Storage) go through adapters. AI models go through the AI gateway. Push
  notifications go through Firebase Cloud Messaging.

3.1.3    Architectural Style: a Modular Monolith with One ML Microservice
Client–server only says that the apps send requests to a server; it does not say how the server side
is built. The specific style of Elha2 is:

 A modular monolith for the backend. All business rules run in one NestJS program, split
  into eight feature modules and five shared services (Section 3.2.1). Each module owns its own
  tables and talks to the others only through named interfaces. The backend is deployed as one
  unit and scaled by running more identical copies of it (Figure 3.2).

3.1.5      Quality Attributes: How the Architecture Supports the NFRs
Each non-functional requirement in SRS Chapter 5 is supported by a specific part of the architec-
ture. Figure 3.2 is a UML deployment diagram: it shows where each part runs, and its green tags
mark the NFR that each part helps to meet.

Availability (NFR-23: 99.5% of each month).                      The target allows about 3.6 hours of down-
time a month. The architecture meets it in three ways. First, there is no single copy of the backend:
at least two identical API instances run behind a load balancer, and because they keep no user
state, either one can answer any request. Second, failures are detected and repaired automatically:
the load balancer checks every instance every 10 s, and the platform restarts a failed one. Third,
when a part is down, the rest keeps working (graceful degradation), as the table shows. Monitoring
alerts the team whenever errors pass 2% (NFR-26).

3.1.6       Technical Feasibility
The design is realistic for our team within one semester. Every part uses mature, well-documented

parts let team members work on different parts at the same time.

 Impact ledger. An ImpactRecord is only ever added, never edited or deleted, and there is at
  most one per action (an order, a donation or a used pantry item), so nothing is counted twice
  (US-9.03). Each record remembers which version of the conversion factors it used, so old totals
  do not change when we update the factors. Factors are saved as new versions, never overwritten
  (US-9.02).

 Stock. A reservation reduces Listing.quantity in a single database step that only succeeds
  if enough bags are left. If two people try to buy the last bag at the same moment, only one
  succeeds (NFR-06).

 Offline copy. The mobile app keeps a copy of the household’s pantry on the phone (SQLite).
  Changes made offline are queued with the time they were made and sent when the phone recon-
  nects; if the same field was changed in two places, the latest change wins (NFR-21, R-13).

 Personal data. We never store card details (NFR-11). Photos sent to AI are deleted by a
  Scheduler job once they are 24 hours old (NFR-14). Storage buckets are private, and the apps
  get short-lived links to view files. AI logs contain no personal data. When a user deletes their
  account, their personal details are removed within 30 days and only anonymous impact numbers
  are kept (US-1.08).

 Jobs. Scheduled jobs are stored in the same PostgreSQL database (pg-boss), so a job and the
  data it changes are saved together, and failed jobs are retried (NFR-19).

 Backups. The database is backed up, encrypted, every day. During the course a nightly GitHub
  Actions job exports it with the Supabase CLI, because the free plan has no automatic backups;
  at launch we use the paid plan’s daily backups. At most 24 hours of data can be lost, and the
  system can be restored within 4 hours (NFR-20).

5. Human Interface Design

5.1     Overview of User Interface
Mobile app (households and deal seekers). The app opens on Home, which shows the items
closest to expiry, today’s deals nearby and the user’s impact this week. A bottom bar gives five
tabs:

 Home: at-risk items with one-tap recipe and donate actions; recipe suggestions (Use it up).

 Pantry: items grouped by fridge, freezer and cupboard and coloured by urgency. A large Add
  food button opens the capture methods: scan receipt, scan barcode, photo, voice and manual.
  After any AI capture the user sees a review screen and confirms with one tap. Once a week the
  pantry offers the 30-second swipe check.

 Deals: a map and a list of nearby surplus; a listing page with price, pickup window, allergens
  and Reserve; after reserving, a QR code and 4-digit code for pickup.

 Donate: choose sealed pantry items to donate, see partner drop-off points on a map, or buy a
  bag for an NGO.

 Impact: kilograms, pounds, CO2 e and meals saved; the monthly waste rate against the Egyptian
  average; How we calculate.

Web portal (businesses, NGOs, administrators, analysts).              After sign-in the portal shows
only the areas of the user’s role in a left-hand menu. Businesses see Today’s orders (with Scan
pickup code), Listings, Donations, Impact and Settings. NGOs see Offers, Pickups and Impact. Ad-
ministrators see Verification, Moderation, Disputes, Settings and Analytics. Analysts see Exports.

Feedback to the user. Every action gets visible feedback: a short message at the bottom of
the screen for success (“7 items added”), inline errors next to the field, a spinner with text for AI
work longer than 1 s (“Reading your receipt. . . ”), confidence percentages and orange highlighting
on uncertain AI results, an offline banner, and an Undo for 10 s after automatic pantry changes.
Push notifications open the related screen directly.

Language and accessibility.       Arabic with a right-to-left (mirrored) layout is the default and
English is available; the wireframes below are shown in English for readability. Every control has
a text label and a screen-reader label, buttons are large enough to tap easily (at least 48 dp), and
colour is never the only signal (SRS NFR-16 to NFR-18).
